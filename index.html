What OPAQUE actually does

No part of this is decorative. Every toggle above changes real output from a real pipeline.

Code security

Raises the effort needed to skim, search, or pattern-match your logic — variable names, literal strings, and structure all change.

IP protection

Keeps proprietary logic — pricing rules, anti-cheat checks, internal APIs — from being trivially copied out of a distributed script.

Anti-tampering friction

Renamed locals and restructured control flow make manual patching of a downloaded script slower and more error-prone.

Reduced readability

Comments and formatting — the parts humans rely on most — are stripped, leaving only what the runtime actually needs.

Roblox-aware

Understands Luau syntax and never renames game, workspace, service names, or other identifiers your code doesn't declare itself.

License enforcement support

A layer that makes it harder — not impossible — to strip out license checks bundled into a script.

Is this safe to use?

Honest answer

OPAQUE transforms your code while keeping its behavior — as long as the transformations you enable are compatible with the runtime you selected, and the output passes the validation step (every result is re-parsed before it's shown to you; if that fails, you get an error instead of broken code).

Obfuscation makes code harder to read and modify. It is not encryption, and it is not a guarantee against reverse engineering. Someone sufficiently determined — with time, tooling, or a decompiler — can still study and potentially reconstruct what obfuscated code does.

For anything sensitive, obfuscation should be one layer among several:

  • Server-side validation for anything that matters (currency, permissions, anti-cheat decisions)
  • Authentication and authorization enforced where the client can't bypass them
  • Secrets and keys kept out of any code that ships to a client entirely
  • Access controls and secure architecture around the sensitive logic itself

Don't rely on obfuscation as your only protection for anything you can't afford to have exposed.

Documentation

Runtimes & Luau

Selecting a runtime changes which grammar the parser accepts — it is not a label. Lua 5.1–5.4, LuaJIT, and Roblox Luau each enable a different feature set (bitwise operators, integer division, goto, Luau type annotations, if-expressions, compound assignment, string interpolation, continue).

Luau code is never downgraded to plain Lua. Type annotations are recognized and erased (they have no effect at runtime), but Luau-specific syntax and semantics are otherwise preserved as written.

Obfuscation levels

LOW — rename locals, strip comments, minify.
MEDIUM — adds string obfuscation and constant transforms.
HIGH — adds safe control-flow wrapping.
EXTREME — adds dead-code insertion on top of HIGH.

Any option can be toggled independently of the preset that's currently selected.

Transformations

Identifier renaming — purpose: shrink meaningful names to short opaque ones. Safety: only applies to locals and parameters resolved through real scope tracking during parsing; a name is only renamed if the parser proved it's a local declaration, never a guess. Globals, table keys, and member names (like Humanoid, WalkSpeed) are left untouched, since renaming them could break references you don't control. Unsupported case: identifiers introduced by constructs the parser doesn't model are left as-is rather than risk a mistake.

String obfuscation — purpose: hide literal text. Method: strings are re-encoded byte-for-byte via string.char with a reversible additive mask per byte, so the exact original bytes are reconstructed at runtime. Limitation: adds real size and a small runtime cost per string.

Constant transform — purpose: hide literal numbers/booleans. Method: small integers become arithmetic identities (e.g. 5 → (8-3)); true/false become equivalent comparisons. Risk: skipped for large numbers, hex/float/exponent forms, to avoid size blow-up or precision issues.

Control flow — purpose: add structural noise. Method: blocks are wrapped in a single-iteration loop with an always-true numeric predicate, terminated by an immediate break — execution order is unchanged. Runtime compatibility: works identically on every supported runtime, since it only uses while/break.

VM protection — purpose: hide string constants behind a small bytecode interpreter instead of visible inline arithmetic. Method: a tiny, plain-text (never itself obfuscated) stack-machine function is injected once per file; each string chunk becomes a flat array of opcodes (push / subtract / byte-to-char / concatenate) that the interpreter executes at runtime to rebuild the original bytes. Safety: the VM only ever operates on self-contained literal values passed to it — it never touches control flow, scoping, or anything referencing your own variables, so it cannot change what your script does. Requires String obfuscation to be on (it has nothing to protect otherwise).

Dead code — purpose: add irrelevant declarations. Method: unused local declarations with unique generated names and literal values — never referenced, never causing side effects.

Minification — removes insignificant whitespace and blank lines; statement boundaries are preserved using Lua's own empty-statement ; separator so nothing is glued together incorrectly.

Comment removal — comments are captured while reading your code and, when this option is off, re-attached near the statement they preceded (line-based, best-effort placement — not guaranteed pixel-identical to the original).

Watermark header — a plain, visible -- comment block at the very top of the output (run ID, level, runtime, timestamp). It's informational only: zero runtime effect, no hidden tracking beyond what's printed in the comment itself, and you can turn it off.

Limitations

  • The parser covers the common core of each grammar used in real-world scripts. Unusual or highly exotic syntax may be reported as a parse error rather than guessed at — see the checklist in the delivery report for exactly what's covered.
  • Table keys and member names are intentionally never renamed, since the parser can't always prove a table isn't accessed dynamically elsewhere (e.g. from another script).
  • Obfuscation increases output size and adds a small amount of runtime overhead, particularly at HIGH/EXTREME.
  • This is not encryption and not a guarantee against reverse engineering — see "Is this safe to use?" above.

Privacy & security

This build runs the entire pipeline — lexer, parser, transformations, code generator, and output validation — as JavaScript in your browser tab. Your code is never transmitted anywhere: there is no upload, no server-side processing, and nothing to store or log, because no backend is involved in producing your result.

This is a deliberate architecture choice: it's strictly more private than a server-side design (nothing ever leaves your machine), at the cost of relying on your browser's JavaScript performance for very large inputs. See the delivery report for how this could be extended with an isolated backend for heavier workloads.
